# ADR-016 — Retrieval service and the RAG boundary

**Status:** Accepted (2026-09-21; hybrid retrieval and the reranking stage added the same day) · **Resolves
provisionally:** OQ-4 (keyword retrieval) · **Touches:** OQ-8 (scope model, provisional), OQ-29
(threshold half decided), OQ-30 (numbered context items) ·
**Refs:** §7.5, §9, §16, §17, §18, §19, §20, §22, §23, §27, §38, §72, §73.

## Context

§17 fixes the stages of retrieval (query preprocessing, vector retrieval, metadata filtering,
candidate selection, reranking, context assembly) and requires each to be independently
testable; §18 asks for a retrieval abstraction that lets ChromaDB be replaced without rewriting
the application layer; §20 fixes what the context builder enforces; §27 fixes the three scopes a
question may cover; §16 and §9 require ownership on every query. The specification does not say
what the unit of "context size" is, how a question is normalised, what a citation-ready evidence
item looks like beyond §23, or whether a document that is being re-processed may still be
served. Reranking and answer generation depend on providers that are not decided (OQ-17).

## Decision

| Concern             | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Boundary            | `doculens.application.rag.RagService` with `RagQuery(owner_id, question, document_ids, collection_id)` is the only entry point for retrieval-augmented work; it returns `RetrievalResult`, never provider or store objects. Answer generation (§21) is added behind the same boundary                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Stages              | One component per §17 stage in `doculens.application.retrieval`: `QueryPreprocessor`, `ScopeResolver` (metadata filtering), a `Retriever` port with `VectorRetriever`, `CandidateSelector`, an optional `RerankingStage` (`doculens.application.reranking`), `ContextAssembler`; `RetrievalService` composes them and the pure rules live in `doculens.domain.retrieval` and `doculens.domain.reranking`                                                                                                                                                                                                                                                                                                                                                                                    |
| Retrieval port      | `Retriever.retrieve(query, scope: SearchFilter, limit) -> Retrieved(hits, usage)`: the §18 abstraction with three implementations: `VectorRetriever` (semantic), `KeywordRetriever` (lexical) and `HybridRetriever` (both). ChromaDB stays behind the `VectorStore` port (ADR-002) and PostgreSQL full-text search behind the repository port; the application layer never sees a store-specific query API                                                                                                                                                                                                                                                                                                                                                                                  |
| Strategy            | `RETRIEVAL_STRATEGY` = `semantic`, `keyword` or `hybrid` (default) selects the retriever at composition time (`build_retriever`); every strategy runs through the same scope filter, candidate selection and context assembly                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Keyword (OQ-4)      | PostgreSQL full-text search over `document_chunks.text` with the `simple` configuration (language-agnostic, no stemming, no stop words) and a GIN expression index (migration `0004`). The query's distinct words (letters and digits in any script, at most 32, at most 64 characters each) are OR-ed with `to_tsquery`; a chunk ranks by the number of distinct query terms it contains, with `ts_rank_cd` cover density (normalised into `[0, 1)`) as the tie-break, so a common word repeated many times never beats several different terms. Terms never carry tsquery syntax, so user input cannot break the query. Exposed as `DocumentContentRepository.search_chunks(query, scope, limit)`, owner-scoped like every read; the in-memory fake ranks by the same distinct-term count |
| Fusion              | `HybridRetriever` runs both retrievers concurrently in a task group (a failing side cancels the other and its error is reported as itself) and merges them by reciprocal-rank fusion (`1 / (60 + rank)` summed per chunk, scaled so that first place on every side is `1.0`), so cosine similarities and full-text ranks combine without calibration and a chunk found by both outranks one found by either; the fused list is cut to the candidate limit and ties break on the vector id                                                                                                                                                                                                                                                                                                   |
| Threshold           | `RETRIEVAL_MIN_SCORE` applies inside `VectorRetriever` only (a similarity means nothing to a keyword rank); the number of neighbours it dropped is reported as `below_threshold`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Reranking (§19)     | `RerankerProvider.rerank(query, documents, top_n) -> [RerankScore(index, score)]` is the §73 port. `RerankingStage` sits between candidate selection and context assembly: every selected candidate (the top-N, at most `RETRIEVAL_CANDIDATES`) is offered to the provider, the provider's best `RERANK_TOP_K` become the final evidence set, renumbered, with `retrieval_score` and `retrieval_rank` kept in the metadata. Selected by `RERANKER_PROVIDER` (`none`, the default, or `fake`); the fake is refused when deployed                                                                                                                                                                                                                                                             |
| Fail-open           | Each provider call is bounded by `RERANK_TIMEOUT_SECONDS` (`asyncio.timeout`). On timeout, any `DependencyUnavailableError`, or a malformed answer (empty, out-of-range, repeated or non-finite scores) the stage returns the retrieval order unchanged and reports `degraded` with the error code; only programming errors propagate. Disabled reranking reports `disabled`, and an empty candidate set reports `skipped`, at no cost                                                                                                                                                                                                                                                                                                                                                      |
| Query preprocessing | Control characters and lone surrogates removed, NFKC normalisation, whitespace collapsed, case kept, bounded by `RETRIEVAL_MAX_QUERY_CHARACTERS`; empty or over-long questions are refused (`INVALID_QUERY`) before any provider call. The original text is kept on the result for persistence (§25). Query rewriting for follow-ups (§26) is a later stage in front of this one                                                                                                                                                                                                                                                                                                                                                                                                            |
| Scope (§27)         | `RetrievalScope`: selected documents, one collection, or (neither given) every document of the owner. Documents and a collection together are refused (`INVALID_RETRIEVAL_SCOPE`) rather than intersected. Unknown or foreign ids answer not found (ADR-013). At most `RETRIEVAL_MAX_SCOPE_DOCUMENTS` may be selected                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| READY only          | The scope is resolved in PostgreSQL to the owner's `READY` documents (one query per question, also for an explicit selection) and every retriever is restricted to exactly those ids. The collection is not repeated in the store filter: the database has already resolved it, so vector metadata that lags behind a move cannot hide evidence. An empty resolved scope short-circuits: no embedding call, no cost                                                                                                                                                                                                                                                                                                                                                                         |
| Source of truth     | Evidence text, page and chunk metadata come from the chunk rows (`DocumentContentRepository.get_chunks`, owner-scoped), not from the copy stored beside the vector. A hit whose chunk is gone, moved or whose content hash differs from the one the vector was built with is dropped as stale. This is defence in depth for §9: text can only ever be read through an owner-scoped query                                                                                                                                                                                                                                                                                                                                                                                                    |
| Candidate selection | Deterministic ranking by `(score desc, vector id)`; drops hits outside the resolved scope, stale, or duplicated by chunk id or content hash. Counts of each are reported in `RetrievalStats`; the evidence records which retriever produced it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Evidence            | `Evidence(document_id, chunk_id, page_number, text, score, metadata)`; `metadata` carries `filename`, `collection_id`, `chunk_index`, `token_count`, `content_hash`, `section_title`, `rank`, `retriever` (`vector`, `keyword` or `hybrid`), `embedding_model`, which is what §23 citations need. `score` is the retriever's score: a cosine similarity, a full-text rank or a fused reciprocal rank. Text is document content and therefore data, never instructions (§22)                                                                                                                                                                                                                                                                                                                 |
| Context (§20)       | `assemble_context`: evidence in rank order under `CONTEXT_MAX_CHUNKS` and `CONTEXT_MAX_CHARACTERS`; when several documents contribute, no document takes more than `CONTEXT_MAX_CHUNKS_PER_DOCUMENT` slots while others wait, then the remaining budget is filled in rank order; duplicates removed; the output keeps the evidence rank order (never re-sorted by score, so reranked and tied evidence stay where their rank put them) with a 1-based `index` per item (the number citations reference, OQ-30). Size is measured in characters until the LLM tokenizer is known                                                                                                                                                                                                             |
| Transactions        | Two short read-only units of work (scope resolution, chunk loading); no database connection is held across the embedding or vector-store call                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Latency budget      | `RETRIEVAL_TIMEOUT_SECONDS` (default 15) bounds the retrievers of one question (embedding, vector search, keyword search) with `asyncio.timeout`; expiry cancels the work and raises `RETRIEVAL_TIMEOUT`, a retryable `DependencyUnavailableError`, since evidence cannot be substituted (§67). Reranking has its own budget and fails open                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

| Not yet             | A hosted reranking adapter (waits for the vendor, OQ-17); conversation-bound scope persistence (OQ-8); an HTTP endpoint (arrives with question answering, §33)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## Alternatives considered

- **Serving evidence text from the vector store.** One round trip fewer, but the vector copy is
  written at indexing time and is neither the source of truth (§7.5) nor owner-checked by the
  database; reading chunks by owner from PostgreSQL costs one indexed query and closes that gap.
- **Filtering non-`READY` documents after the search.** Simpler, but a re-processing document's
  old vectors would compete for the candidate slots and be silently discarded; passing the exact
  id set to the store keeps the candidate list meaningful and the exclusion explicit.
- **Intersecting selected documents with a collection.** The specification lists three scopes;
  a combined one has no defined meaning, so it is refused until a requirement asks for it.
- **Interleaving documents in the context output.** Would put weaker evidence ahead of stronger
  evidence; diversity is applied to slot allocation only and the output stays in rank order.
- **Language-specific full-text configuration (`english`).** Stemming and stop words improve
  recall for one language and hurt every other; the corpus language is unspecified, so the
  language-agnostic `simple` configuration is used and a per-collection language can be added
  behind the same repository method later.
- **ChromaDB `where_document` substring search for keywords.** No ranking and a store-specific
  query API; the chunk text already lives in PostgreSQL, which ranks and indexes it.
- **Weighted score fusion.** Needs calibrated scores from both sides; reciprocal-rank fusion
  is rank-only, has one well-known constant and no tuning surface to get wrong.
- **Degrading hybrid retrieval to keyword-only when the embedding provider is down.** Rejected
  for now: a silently narrower search would change answer quality without the caller knowing;
  the request fails as retryable instead (§67) and the outage is visible. Revisit with the
  evaluation suite if availability data argues for it.
- **Failing the question when the reranker fails.** Reranking improves ordering; it is not
  what makes an answer grounded. A degraded ordering with the outcome reported beats an error
  (§67), and the evaluation suite can measure both paths.
- **Reranking inside each retriever.** Would rerank twice under the hybrid strategy and hide
  the stage from the pipeline; one stage after fusion and selection keeps §17's order.
- **Token-based context budget.** The right unit once the LLM is chosen (OQ-17); the regex
  tokenizer of ADR-003 is not that model's tokenizer, so characters are the honest measure now.

## Consequences

- New port methods `DocumentContentRepository.get_chunks(owner_id, chunk_ids)` and
  `search_chunks(query, scope, limit)` on the SQLAlchemy adapter and the in-memory fake; migration
  `0004` adds the full-text GIN index.
- New settings `RETRIEVAL_STRATEGY`, `RETRIEVAL_*` (including `RETRIEVAL_TIMEOUT_SECONDS`),
  `RERANKER_PROVIDER`, `RERANK_*` and `CONTEXT_*`; `.env.example` documents them.
- Review (2026-09-21): keyword stop words are not removed (language-specific, OQ-4), so under
  the keyword-only strategy common words match broadly; the hybrid default and reranking
  absorb this, and the evaluation suite (§62) should measure it. Query terms longer than 64
  characters are ignored. The corpus checkpoint (2026-09-21) showed occurrence-based ranking
  letting a chunk repeating a common word outrank the answer, hence the distinct-term rule
  above. `SearchHit`/`VectorMetadata` double as the keyword hit shape; the
  application layer imports no ChromaDB, PostgreSQL or LangChain symbol (enforced by the
  architecture test), and LangChain is not used anywhere in the retrieval path.
- The test doubles `BagOfWordsEmbeddingProvider` (word-overlap vectors) and `FakeReranker`
  (word-overlap scores, scriptable delays and failures) let retrieval tests assert on ranking
  and degradation without a model; both stay in `doculens.testing`.
- Question answering, citations and the conversation endpoints build on `RetrievalResult`
  (`context.items[n].index` is the citation reference); the evaluation harness (§62, §63) can
  score retrieval on its own through `RagService.retrieve`.
